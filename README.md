# Assignment

## 注释规范

### 1. 文件头注释 (File Header)

每个 `.c` 和 `.h` 文件开头应包含文件摘要，方便他人快速了解该文件作用。

```c
/**
 * @file student_manager.c
 * @brief 学生管理系统的核心业务逻辑实现
 * @author YourName
 * @date 2026-05-26
 * @version 1.0
 */

```

### 2. 函数头注释 (Function Header)

函数头是注释的重中之重。它必须包含接口描述，让调用者无需阅读函数内部代码即可使用该函数。

- **要素**：功能描述、参数说明 (`@param`)、返回值说明 (`@return`)、前置/后置条件。

```c
/**
 * @brief 按学号删除学生记录
 * @param head 指向链表头节点的二级指针
 * @param id   要删除的学生学号
 * @return int  成功返回 1，未找到返回 0
 * @note 该函数会修改链表结构，调用后需注意释放内存
 */
int delete_by_id(Student** head, int id) {
    // ...
}

```

### 3. 行内与代码块注释 (Code Comments)

- **避免“显而易见”的注释**：不要写 `i++; // i 加 1` 这种废话。
- **解释“Why”**：如果代码使用了某种特殊的技巧（如位运算优化、为了兼容特定硬件的 Hack），必须写清楚原因。
- **TODO 标记**：使用 `// TODO:` 标记尚待完成或存在潜在性能问题的代码。

```c
// 使用掩码方式优化状态判断，避免分支预测失败 (Why)
status &= ~MASK_READY;

// TODO: 此处文件读取在数据量极大时性能较低，后续考虑引入索引文件
load_file();

```

---

### 4. 注释风格规范

- **风格统一**：
- 单行注释：`// ...`
- 多行注释：`/* ... */` 或 `/ ... */`（推荐 Doxygen 风格的 `/`，因为它可以自动生成技术文档）。

- **对齐与布局**：保持注释与代码的对齐，不要让注释破坏代码的视觉结构。
- **语言选择**：在国际化项目中，建议使用英文。如果在中文开发团队中，建议使用清晰的中文，但技术术语保持原词。

---

### 5. 为什么需要规范的注释？(Checklist)

| 注释类型                  | 解决的问题                                         |
| ------------------------- | -------------------------------------------------- |
| **Why (意图)**            | 告诉后续维护者为什么要这样写，避免“不敢改代码”。   |
| **Limitations (限制)**    | 告诉他人此函数的边界在哪（例如：参数必须大于 0）。 |
| **Side Effects (副作用)** | 提醒他人此操作是否会修改全局变量或产生 IO 操作。   |
| **Doxygen 兼容**          | 自动提取注释生成文档，省去额外写说明文档的时间。   |

---

### 专家贴士：注释的“三重境界”

1. **初级**：注释代码在做什么（What）。（**大多情况不需要，代码本身已说明**）
2. **中级**：注释代码是怎么做的（How）。（**适用于复杂算法**）
3. **高级**：注释为什么这样做（Why）。（**核心价值所在**）

**建议**：
如果你的项目将来要生成开发文档，请直接采用 **Doxygen** 格式（即代码中看到的 `@brief`, `@param` 这种）。这是目前 C/C++ 领域最标准的注释规范，像 Linux 内核、FreeRTOS 等顶尖项目都在使用。
